# 约球 Web 应用产品设计文档（V0.1）

## 1. 文档信息
- 文档日期：2026-04-16
- 版本：V0.1（可评审草案）
- 目标产品：约球 Web 应用（默认先聚焦乒乓球）
- 当前假设：面向中国城市用户，先做移动端 Web（H5）优先的 MVP

## 2. 背景与问题定义
线下打球存在三个高频痛点：
- 人难凑：临时想打球但找不到水平匹配、距离合适的球友
- 场难约：球馆信息分散，空闲时段不透明，沟通成本高
- 信任弱：陌生人约局存在爽约、水平不符、沟通不畅问题

产品目标是用“发布约局 + 匹配球友 + 场地协同 + 履约保障”形成闭环，降低从“想打球”到“打上球”的时间和失败率。

## 3. 产品目标与成功指标
## 3.1 北极星指标
- 成功开打场次（7 日内实际完成的约局数）

## 3.2 MVP 阶段关键指标（上线后 8 周）
- 发起约局转化率 >= 35%（访问发起页到提交成功）
- 约局成局率 >= 45%（已发起约局中成功凑齐人数）
- 爽约率 <= 15%
- 首次约局完成时间中位数 <= 24 小时
- 7 日留存 >= 20%

## 4. 目标用户与使用场景
## 4.1 目标用户
- 学生与白领业余爱好者：临时性强，时间碎片化
- 轻竞技用户：关注对手水平接近与比赛体验
- 球馆周边用户：希望快速匹配同区域球友

## 4.2 核心场景
- 下班后临时约一场（2 小时内）
- 周末提前组局（1-3 天）
- 固定球友临时缺席，快速补位

## 5. 产品范围（MVP）
## 5.1 In Scope
- 手机号/微信快捷登录（至少保留一种可用登录）
- 创建约局：运动类型、时间、地点、人数、水平、费用说明
- 浏览与筛选约局：按距离、时间、水平、人数状态
- 申请加入/主理人同意机制
- 站内即时聊天（至少支持文本）
- 成局提醒与开打前提醒
- 履约反馈：完成后互评 + 爽约标记

## 5.2 Out of Scope（MVP 不做）
- 联赛与复杂积分体系
- 多运动深度规则定制
- 复杂支付分账（先做“线下 AA/到场支付”）
- 企业级球馆 SaaS 管理

## 6. 方案对比（2-3 种）与推荐
## 6.1 方案 A：约局广场 + 群聊协同（最轻量）
- 说明：以“发局/加局”为核心，不做自动匹配引擎，仅靠筛选和申请流程
- 优点：上线快、成本低、验证最直接
- 缺点：匹配效率依赖活跃度，冷启动期体验一般

## 6.2 方案 B：约局广场 + 智能推荐（推荐）
- 说明：在方案 A 基础上加入“候选局推荐/候选球友推荐”（规则优先，非重算法）
- 优点：提升成局率与响应速度，仍可控成本
- 缺点：需要额外的数据结构与推荐策略迭代

## 6.3 方案 C：先做“场馆档期 + 预订”再叠加社交
- 说明：以场地预订为中心，约球作为附属流程
- 优点：商业路径较清晰（平台抽佣/服务费）
- 缺点：依赖球馆合作，商务与履约链条更重，MVP 风险高

## 6.4 推荐结论
推荐采用方案 B：先做“可用且轻量”的约局闭环，再用规则推荐提升效率。  
理由：相比 A 更容易拉起成局率；相比 C 更不依赖线下商务资源，适合先验证用户价值。

## 7. 核心用户流程
## 7.1 发起方流程
登录 -> 创建约局 -> 发布成功 -> 处理申请 -> 成局 -> 到场开打 -> 赛后反馈

## 7.2 参与方流程
登录 -> 浏览/筛选约局 -> 申请加入 -> 通过后进聊天 -> 开打提醒 -> 到场 -> 赛后反馈

## 7.3 异常流程
- 无人响应：系统在 T+2 小时推荐替代时间/邻近球馆/相近球友
- 临时取消：引导主理人一键改期并通知所有成员
- 爽约：记录爽约标签，影响后续可见性和推荐权重

## 8. 功能设计
## 8.1 约局发布
- 必填：运动、时间、地点、人数上限、水平区间
- 选填：费用规则、备注、是否接受新手
- 校验：时间不得早于当前 +30 分钟；人数上限需合理范围

## 8.2 约局发现
- 列表卡片：时间、地点、剩余席位、发起人信誉
- 筛选项：距离、开打时间、水平、仅看可直接加入
- 排序：优先即将开始且距离近

## 8.3 申请与审核
- 默认“需审核”；可配置“自动通过”
- 主理人 30 分钟未处理时提醒
- 重复申请限制与频率限制，防骚扰

## 8.4 聊天与通知
- 局内聊天：文本、系统消息（通过/拒绝/改期）
- 通知渠道：站内通知 + 可扩展短信/微信模板消息
- 关键节点提醒：开打前 2 小时和 30 分钟

## 8.5 信任与安全
- 赛后互评（简版：1-5 分 + 标签）
- 爽约申诉入口（人工审核后修正）
- 举报与拉黑（最小可用闭环）

## 9. 信息架构与页面清单
- 首页（推荐局/附近局）
- 约局广场（筛选 + 列表）
- 约局详情（申请、成员、规则、聊天入口）
- 创建约局页
- 我的约局（我发起/我参与）
- 消息中心
- 个人主页（信誉、历史场次）

## 10. 数据模型（MVP）
## 10.1 用户 User
- id, nickname, avatar, city, skill_level, credit_score, created_at

## 10.2 约局 Match
- id, sport_type, start_time, venue_id, host_user_id, max_players, level_min, level_max, status, note

## 10.3 参与申请 JoinRequest
- id, match_id, user_id, status(pending/approved/rejected/canceled), created_at

## 10.4 聊天消息 Message
- id, match_id, sender_user_id, content, type(text/system), created_at

## 10.5 评价 Review
- id, match_id, reviewer_id, reviewee_id, score, tags, comment

## 11. 非功能需求
- 性能：列表首屏加载 <= 2 秒（4G 环境）
- 可用性：核心流程可在 3 分钟内完成一次发局
- 安全：登录态与接口鉴权、防刷、敏感词审核
- 可观测：关键埋点（曝光、申请、通过、开打、评价）

## 12. 风险与应对
- 冷启动不足：以“学校/园区/球馆周边”做局部高密度投放
- 爽约破坏体验：引入信用分与限制策略
- 场馆信息不准：允许用户纠错并建立热度优先展示
- 通知触达差：关键提醒支持多通道兜底

## 13. 测试与验收
## 13.1 验收标准（MVP）
- 用户可独立完成：注册登录、发局、申请、审核、聊天、评价
- 关键异常可闭环：取消、改期、拒绝、举报
- 埋点数据可追踪成局漏斗

## 13.2 测试范围
- 功能测试：核心流程与异常流程
- 接口测试：鉴权、参数边界、并发申请
- 体验测试：移动端适配、弱网表现、通知时效

## 14. 里程碑建议
- 第 1 周：需求冻结 + 原型 + 技术方案确定
- 第 2-3 周：MVP 开发（账户、约局、申请、消息）
- 第 4 周：联调与灰度内测
- 第 5 周：小范围上线 + 数据复盘

## 15. 待你确认的关键决策
- 运动范围：只做乒乓球，还是首发支持“羽毛球 + 乒乓球”
- 审核机制：默认“主理人审核”还是“自动通过”
- 商业化时点：MVP 先不收费，还是从场馆导流收服务费
